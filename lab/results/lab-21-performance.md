## Lab 21: イベント負荷と検知遅延・リソース消費の実測（研究C）

第11章（Runtime Detectionの限界と評価）の研究Cを、実機で検証した記録。

### インシデント：無制限の負荷生成がDocker Desktop VM全体を無応答にした

最初の負荷生成Podは、CPU上限を設けずに`while true; do for i in $(seq 1 50); do /bin/true & done; wait; done`という無限ループを実行した。これにより：

- `attack-lab-control-plane`のCPU使用率が**281%**まで上昇
- kube-apiserverへの接続が`TLS handshake timeout`で失敗
- **`docker ps`すら6分以上応答しなくなった**
- 同じDocker Desktop VM上で動く**他のkindクラスタ（tuning-lab, sysdig-handson, obs-cost）すべてに影響**が及んだ

Docker Desktopの再起動が必要になった（再起動後、全コンテナは正常に復帰）。

**これ自体が研究Cの最も重要な実証結果である**：本文で想定していた「イベントレートが閾値を超えると検知遅延が悪化し、イベント欠落が始まる」という緩やかな劣化モデルは、**少なくともリソースが共有された環境では成立しなかった**。実際に起きたのは、**Falcoのイベント欠落検知が働く前に、ホストそのものがCPU枯渇で丸ごと無応答になる**という、より急峻で危険な故障モード。

### 修正：CPU上限を設けた有界な負荷生成で再実験

教訓を反映し、`resources.limits.cpu: "1"`を設定した、**実行回数が有限（5000プロセス起動で終了）**の負荷生成に変更して再実行：

```yaml
resources:
  limits:
    cpu: "1"
    memory: "128Mi"
```

### 実測結果

| 項目 | 値 |
|---|---|
| 負荷生成の継続時間 | 約11秒（CPU上限により想定より短時間で完了） |
| 観測期間中のイベント数 | 3,371,457件（52秒間） |
| 概算イベントレート | **約65,000 events/sec**（ノード全体・他クラスタ分含む） |
| イベント欠落数（`n_drops_total`） | **0** |
| Falco自身のCPU使用率 | 7.5%（アイドル時）→ 13.4%（負荷時） |
| ホスト全体のCPU使用率 | 29.4%（アイドル時）→ 66.6%（負荷時） |

**約65,000 events/secまでは、イベント欠落は一切発生しなかった**。これは本文が想定していた「50,000 events/sec前後から欠落が始まる」という仮の数値よりも、modern eBPFドライバは高いレートまで耐えられることを示している（ただし、この数値はDocker Desktop VM上の共有環境での計測であり、専用ノードでの数値とは異なる可能性がある）。

### 計測上の制約

- 本ラボは**4つのkindクラスタが同一Docker Desktop VMを共有**する環境のため、「純粋に本クラスタの負荷だけによる変化」を正確に切り分けることはできない。負荷試験後もCPU使用率がベースラインに戻りきらなかったのは、他クラスタの並行アクティビティの影響の可能性がある。
- イベント欠落が実際に発生する閾値そのものは、**安全に測定することができなかった**。無制限の負荷生成がホスト全体を無応答にするため、閾値ギリギリを狙った精密な測定は、共有環境では現実的にリスクが高すぎる。

### 考察（本文修正用）

- 「イベントレートが閾値を超えると検知遅延が悪化し、イベント欠落が始まる」という段階的な劣化モデルは、**少なくとも本ラボの環境では確認できなかった**。代わりに「欠落が起きる前に、ホストが丸ごと無応答になる」という、より急峻な故障モードが実際に発生した。
- 具体的な数値（50,000 events/secで欠落開始、等）は架空の想定であり、実測では65,000 events/secまで欠落ゼロだった。本文の数値は全て実測値に置き換える、または「環境依存で一般化できない」ことを明記する。
- **「負荷試験は必ずリソース上限を設けて行う」**という運用上の教訓も、本書に追加する価値がある（これ自体、実際に失敗してから学んだ教訓）。
